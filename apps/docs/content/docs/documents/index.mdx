---
title: Form documents
description: Describe a form as data, for form builders and forms stored in a database, and render it through your registry.
---

A typed config is how a form is written in code: the compiler checks every field against its
widget, and the form ships with the app. A **form document** is how a form is stored: JSON with a
format version that a builder writes and a database keeps, so the form changes without a deploy.
`@formdef/document` reads such a document, checks it, renders it through the widgets of your
registry and validates its answers, in the form and on a server.

| The form is | Write it as |
| --- | --- |
| written by a developer, as part of the app | a typed config |
| put together in a builder, or stored per customer in a database | a form document |

Nothing types a document's fields at compile time, so a document is checked when it is read. What
a field may be is decided in code, once: by the project's [field kinds](/documents/field-kinds).

## The shape

```json
{
  "format": 1,
  "items": [
    { "type": "field", "key": "f1", "kind": "text", "label": "Name", "required": true },
    {
      "type": "row",
      "items": [
        { "type": "field", "key": "f2", "kind": "email", "label": "Email" },
        { "type": "field", "key": "f3", "kind": "text", "label": "Phone" }
      ]
    },
    {
      "type": "section",
      "label": "Callback",
      "items": [
        { "type": "field", "key": "f4", "kind": "checkbox", "label": "Call me back" },
        {
          "type": "field",
          "key": "f5",
          "kind": "date",
          "label": "On",
          "description": "A weekday",
          "required": true,
          "visibleWhen": { "field": "f4", "op": "isTrue" }
        }
      ]
    }
  ]
}
```

- `format` is the version of the format the document was written with; `FORMAT_VERSION` is the
  one this release writes. A document of a newer format is refused when it is read.
- A document holds either `items`, a plain form, or `steps`, filled in one at a time. A step has a
  `key`, a `label`, an optional `description` under the label in the stepper, an optional
  `visibleWhen`, optional [jumps](#jumps) under `next`, and its `items`.
- An item is a **field**, a **block** of content without an answer, a
  [**computed value**](#computed-values), a **row** of fields, blocks and computed values side by
  side, a **section**: a `label` over its `items`, and an optional `description` under it, or a
  [**repeat**](#repeats) of items the person fills in as often as needed. A section inside a
  section is a group that reads like one question, such as an address; a third level is not
  allowed.
- A block has a `key`, the `kind` of a registered [block kind](/documents/field-kinds#block-kinds),
  and optionally `settings` and `visibleWhen`. It gives no answer and is not validated; a condition
  cannot name it.
- A field has a `key`, the `kind` of a registered field kind and a `label`, and optionally a
  `description` between the label and the control, `required`, `visibleWhen`, `settings`,
  [`messages`](/documents/validation-and-answers#error-texts), its own error texts, and
  [`checks`](/documents/validation-and-answers#checks-against-other-answers) against other answers.
- **Keys** are generated by a builder and never shown. A field key is unique in the whole document,
  across steps too, and holds no dot or bracket, since it becomes a path in the form's values. The
  values of a document with steps are nested by step key, `{ s1: { f1: 'Ada' } }`; those of a
  plain form are flat.
- `required` is `true`, `false` (the default) or a condition. `visibleWhen` takes a condition on a
  step, section, row or field; without one, it always shows.
- `settings` holds the values of the field kind's [settings](/documents/field-kinds#settings), by
  name, such as the options of a choice or the unit of a number.
- `display` says how the form of steps, a step, a section, a row or a repeat looks: the `kind` of a
  registered [display kind](/documents/field-kinds#display-kinds) and its `settings`, such as
  `{ "kind": "rail" }` at the root for a stepper drawn as a rail. Without one, each renders as its
  slot does.

### Settings that follow an answer

A setting whose field kind marks it as `varies` may follow an answer. Its `cases` are checked in
order, and the value of the first whose condition holds applies; `otherwise` applies when none
does:

```json
{
  "type": "field",
  "key": "f7",
  "kind": "decimal",
  "label": "Living area",
  "settings": {
    "unit": {
      "cases": [{ "when": { "field": "f6", "op": "equals", "value": "o1" }, "value": "m²" }],
      "otherwise": "sq ft"
    }
  }
}
```

The field shows the unit that applies while the answers change; the validator and
[`describeAnswers`](/documents/validation-and-answers#describing-answers) use it too. A setting
whose field kind does not mark it takes a plain value.

### Texts that follow an answer

A text may follow an answer the same way, with `cases` and `otherwise`: the label and
description of a field, the description of a step or section, and the label and description of an
option. The labels of steps and sections stay fixed, since the stepper and the section show them
for the whole form.

```json
{
  "type": "field",
  "key": "f8",
  "kind": "number",
  "label": {
    "cases": [{ "when": { "field": "f6", "op": "equals", "value": "o1" }, "value": "Number of radiators" }],
    "otherwise": "Number of heating circuits"
  }
}
```

A condition of a text names a field that comes earlier, as every condition does. The case is
chosen first, then the language, then the placeholders.

### Placeholders

A text may name the answer of an earlier field as `{key}`, such as `"Thank you, {f1}."`. The
placeholder takes the answer as its value type writes it: text, a decimal or a date as entered, a
number, the label of the option chosen, the labels of several joined with commas. An answer that
is empty or does not show, and a boolean, give nothing. `{{` and `}}` write a brace.

Placeholders work in every text that may follow an answer, and in text settings. In a field's own
[error texts](/documents/validation-and-answers#error-texts) they name the issue's params and the
`label` instead. The labels of
steps and sections name no answers; `checkDocument` reports a placeholder there as `fixedText`, and
one on a field that does not exist or comes later as `unknownField` or `laterField`.

### Formatted descriptions

The descriptions of fields, options, sections and steps may carry limited formatting, written as
Markdown: `**bold**`, `*italics*`, links as `[text](https://…)` and paragraphs separated by a blank
line. A link opens only an `https:` or `mailto:` address, and a step's description shows its links
as text, since the stepper shows it inside a button. HTML stays text, and other Markdown, such as a
heading or a list, shows as its text. Labels stay plain. An answer a placeholder names shows as it
was typed, never as formatting or a link.

### Languages

A document in several languages names them at the root, as language codes. Every text then takes
either a string, which holds for every language, such as a unit, or its translations:

```json
{
  "format": 1,
  "languages": ["de", "en"],
  "items": [
    {
      "type": "field",
      "key": "f1",
      "kind": "decimal",
      "label": { "de": "Wohnfläche", "en": "Living area" },
      "settings": { "unit": "m²" }
    }
  ]
}
```

- The texts are the labels and descriptions of steps, sections and fields, the labels and
  descriptions of options, and the values of a field kind's [text settings](/documents/field-kinds#settings),
  such as a placeholder.
- [`checkDocument`](/documents/builders#reading-and-checking) reports a translation that leaves out
  one of the languages, and one into a language the document does not name.
- `createDocumentForm`, `createValidator` and `describeAnswers` take a `language`. Without one, or
  with one the document does not name, the first language applies. A field kind's `props`
  receive its settings in that language, so no field kind deals with translations.

## Conditions

A condition compares one field, or combines conditions with `all` or `any`:

```json
{
  "any": [
    { "field": "f1", "op": "equals", "value": "o2" },
    { "field": "f4", "op": "atLeast", "value": 3 }
  ]
}
```

The field compared comes earlier in the document than the condition that names it. A field that
does not show counts as empty in the conditions after it, whatever value it still holds.

The operators belong to the value type of the field compared, and each says what it compares with,
as a setting: `op` is a name and `value` any JSON, and
[`checkDocument`](/documents/builders#reading-and-checking) checks both against the catalog. The
built-in value types have these:

| Value type | Operators | `value` |
| --- | --- | --- |
| `text` | `isFilled`, `isEmpty` | none |
| `choice` | `equals`, `notEquals` | an option's value |
| | `in`, `notIn` | a list of option values |
| | `isFilled`, `isEmpty` | none |
| `choices` | `includes`, `excludes` | an option's value |
| | `isFilled`, `isEmpty` | none |
| `boolean` | `isTrue`, `isFalse`, `isFilled`, `isEmpty` | none |
| `number`, `decimal` | `equals`, `notEquals`, `lessThan`, `atMost`, `greaterThan`, `atLeast` | a number |
| | `isFilled`, `isEmpty` | none |
| `date` | `equals`, `before`, `onOrBefore`, `after`, `onOrAfter` | a date as an ISO string, such as `2026-05-01` |
| | `isFilled`, `isEmpty` | none |
| a [value type of your own](/documents/field-kinds#value-types) | its own operators, `isFilled`, `isEmpty` | what each operator compares with |
| a [repeat](#repeats), by its number of entries | `atLeast`, `atMost` | a whole number |
| | `isFilled` (one entry or more), `isEmpty` | none |

- An empty field equals nothing and comes in no order, so of the comparisons only `notEquals`,
  `notIn` and `excludes` hold for it.
- A boolean counts as filled only when it is true: `isFalse` holds for a checkbox left unticked.
- A decimal is compared as a number, and a date with a time by its day.

A builder offers only the operators of the field's value type and renders the input for `value`
from the operator's setting; `checkDocument` reports an operator the value type does not have and
a `value` that does not fit, is missing, or is given to an operator that compares with nothing.

### Comparing with another answer

`valueFrom` names an earlier field whose answer the field is compared with, in place of `value`:

```json
{ "field": "f5", "op": "atMost", "valueFrom": "f4" }
```

- The other field obeys the rules of every condition: it exists and comes earlier.
- Its value type compares as the operator's setting: a decimal or a number for a number, a date
  for a date, a choice for an option, several choices for a list of options, text for text.
  `checkDocument` reports any other pairing as `valueMismatch`.
- While the other field has no answer, the comparison does not hold, negated or not.
- A comparison holds either `value` or `valueFrom`; `readDocument` refuses one with both, and
  `checkDocument` reports the `value` of one built that way as `valueMismatch`.

## Jumps

A step may jump forward when the person moves on: the first jump under `next` whose condition
holds goes on with the step it names, and the steps in between do not show.

```json
{
  "key": "s1",
  "label": "House",
  "next": [{ "when": { "field": "f1", "op": "equals", "value": "o2" }, "step": "s4" }],
  "items": []
}
```

- A jump is visibility in disguise: the steps it passes over are left out of the stepper, not
  validated, and their answers are left out of the validator's `value` and `describeAnswers`.
- Its condition reads the answers of its own step and those before it.
- It goes forward only, so the form cannot loop. `checkDocument` reports a jump to a step the
  document does not hold as `unknownStep`, and one to the step itself or an earlier one as
  `backwardJump`.
- `{ "when": …, "end": "e1" }` ends the form instead: moving on from the step submits it with the
  answers so far, the steps after it do not show, and the [ending](#endings) `e1` applies.

## Intro

A document may open with an intro under `intro` at the root: blocks and the label of the button
that starts the form.

```json
{ "intro": { "items": [{ "type": "block", "key": "b1", "kind": "notice", "settings": { "body": "This takes about **5 minutes**." } }], "start": "Start" } }
```

- `createDocumentForm` shows the intro and its start button first, then the form, which takes the
  focus. `startButton` passes a button of the project's own, which receives `label` and
  `onStart`; without it the button is a plain `<button type="button">`.
- The intro shows before any answer, so its texts and the button's label name none:
  `checkDocument` reports a placeholder in them as `fixedText`. They may be translated.

## Endings

A document may name what a person sees once the form is submitted, under `endings` at the root:
each a `key`, an optional `when` and blocks, whose texts may name any answer.

```json
{
  "endings": [
    { "key": "e1", "items": [{ "type": "block", "key": "b1", "kind": "notice", "settings": { "body": "We only plan heat pumps for houses you own." } }] },
    { "key": "e2", "when": { "field": "f8", "op": "isTrue" }, "items": [{ "type": "block", "key": "b2", "kind": "notice", "settings": { "body": "You qualify for funding, {f1}." } }] },
    { "key": "e3", "items": [{ "type": "block", "key": "b3", "kind": "notice", "settings": { "body": "Thank you." } }] }
  ]
}
```

- A jump that ends the form applies its ending. Otherwise the first ending whose `when` holds
  applies, and one without `when` is the fallback. An ending a jump names, such as `e1` above,
  applies only through its jump, never in this order.
- Once the form is submitted and `onSubmit` is done, `createDocumentForm` shows the ending that
  applies in place of the form and moves the focus to it; an `onSubmit` that fails, or an ending
  none of whose blocks shows, keeps the form.
  `showsEnding: false` leaves the form in place, for a page of the project's own or a redirect.
- `endingOf(document, catalog, { values })` tells which ending applies, so a server and a
  confirmation email agree with the page.
- `checkDocument` reports a jump to an ending the document does not hold as `unknownEnding`, and a
  fallback before the last ending taken in order as `fallbackNotLast`. Block keys share the keys of
  fields.

## Repeats

A repeat holds items the person fills in as often as needed, one **entry** each, such as one per
resident:

```json
{
  "type": "repeat",
  "key": "r1",
  "label": "Residents",
  "addLabel": "Add person",
  "removeLabel": "Remove person {n}",
  "entryLabel": "Person {n}",
  "min": 1,
  "max": 6,
  "items": [
    { "type": "field", "key": "f2", "kind": "text", "label": "Name" },
    { "type": "field", "key": "f3", "kind": "yesNo", "label": "Works" },
    {
      "type": "field",
      "key": "f4",
      "kind": "date",
      "label": "Working since",
      "visibleWhen": { "field": "f3", "op": "isTrue" }
    }
  ]
}
```

- `label`, `addLabel` and `removeLabel` are required; `entryLabel`, the title over each entry,
  `min`, `max`, `visibleWhen` and `display` are optional. The texts may be translated and name no
  answers; `removeLabel` and `entryLabel` name the entry's number as `{n}`.
- `min` and `max` are whole numbers of 0 or more, the fewest and the most entries.
- Its items are fields, blocks, computed values, rows and sections, within the same two levels of
  sections, counting those around the repeat. A repeat holds no other repeat.
- Inside a repeat, a condition, placeholder or expression that names a field of the repeat reads
  that field of the same entry: above, `f4` shows for each resident who works. It may also name
  fields before the repeat. Outside the repeat, no entry is meant, so nothing there names a field
  inside it.
- A condition after the repeat names the repeat itself to compare its number of entries, such as
  `{ "field": "r1", "op": "atLeast", "value": 2 }`. A repeat that does not show counts as one
  without entries.
- The repeat's key shares the keys of fields. Its value is a list of entries, one object each:
  `{ "r1": [{ "f2": "Ada" }, { "f2": "Max" }] }`.
- `createDocumentForm` renders a repeat through the registry's
  [array frame](/guides/arrays#a-frame-of-your-own), with `addLabel` and `removeLabel` on its
  controls, and gives the frame the props `label`, `min` and `max`, with an `entryLabel` also
  `itemLabel`, a function of an entry's index that returns its title, next to those of its
  `display`.
  The form starts with as many empty entries as `min` asks for.
- `checkDocument` reports a field inside a repeat named from outside it as `repeatField`, a repeat
  inside a repeat as `nestedRepeat`, and a `min` above `max` as `minAboveMax`.

## Computed values

A computed value works something out from earlier answers, such as a total or a share, and is
used like an answer nobody types:

```json
{
  "type": "computed",
  "key": "c1",
  "label": "Heated share",
  "valueType": "number",
  "expression": {
    "op": "round",
    "digits": 1,
    "args": [
      {
        "op": "multiply",
        "args": [{ "op": "divide", "args": [{ "field": "f4" }, { "field": "f3" }] }, { "value": 100 }]
      }
    ]
  }
}
```

An expression is data, never code the package runs:

| Expression | Comes to |
| --- | --- |
| `{ "field": "f3" }` | the answer of an earlier field or computed value: a number, decimal, text or date |
| `{ "value": 12.5 }` | a constant, a number or a text |
| `{ "op": "add", "args": [ … ] }` | the sum; `subtract`, `multiply` and `divide` likewise, `min` and `max` the smallest and largest |
| `{ "op": "round", "args": [x], "digits": 1 }` | `x` rounded, to no digits without `digits` |
| `{ "op": "otherwise", "args": [x, fallback] }` | `x`, or `fallback` when `x` is empty |
| `{ "op": "daysBetween", "args": [from, to] }` | the days from one date to the other, by their day |
| `{ "op": "concat", "args": [ … ] }` | a text of its operands joined: an answer read as its [placeholder](#placeholders) writes it, such as a decimal with its comma, anything else as plain digits or text |
| `{ "op": "count", "field": "f4" }` | how many options a field with several choices holds, 0 without any |
| `{ "op": "score", "field": "f4" }` | the sum of the `score` of each option chosen, 0 without any; an option without a `score` counts 0 |
| `{ "op": "sum", "field": "f5" }` | the sum of a number field of an earlier [repeat](#repeats) over its entries, 0 without any; `min` and `max` the smallest and largest, empty without any |
| `{ "op": "count", "field": "r1" }` | how many entries an earlier repeat holds |
| `{ "op": "countWhere", "field": "r1", "when": condition }` | how many entries of an earlier repeat the condition holds for; it reads each entry's fields and those before the repeat |
| `{ "cases": [{ "when": condition, "value": x }], "otherwise": y }` | the `value` of the first case whose [condition](#conditions) holds, `y` when none does, shaped like a [setting that follows an answer](#settings-that-follow-an-answer) |

- An empty operand makes an empty result, unless `otherwise` replaces it, so a total does not
  pretend to be complete while a part is missing. Dividing by zero is empty too.
- `valueType` is `number`, `text` or `date`, what the expression comes to; `checkDocument` reports
  another as `resultMismatch`, an unknown operation as `unknownOperation`, and an operand of the
  wrong kind or number, such as text to `add`, as `operandMismatch`.
- An expression reads earlier answers only, as a condition does; `visibleWhen` decides whether the
  value counts.
- Conditions compare it, placeholders name it, and the validator's `value` and `describeAnswers`
  hold it, worked out again; a value sent under its key is never taken. It has no control in the
  form: a block shows it through a placeholder, such as a notice reading `Heated share: {c1} %`.
- An option may carry a `score`, any number, for `score`: `{ "value": "o2", "label": "Oil", "score": 2 }`.

## A first form

<Steps>
<Step>

### Install the package

```npm
npm install @formdef/document @formdef/core @tanstack/react-form
```

</Step>
<Step>

### Fetch the field kinds

After the [setup](/installation#the-widgets-for-shadcn), fetch the field kinds of the shadcn
registry:

```npm
npx shadcn@latest add @formdef/field-kinds
```

It writes `lib/formdef/field-kinds.ts`, which exports them as a `catalog`. Its field kinds name the
widgets `text`, `textarea`, `number`, `checkbox`, `radio`, `select`, `checkboxes` and `date`.
Register each under that name in `lib/formdef/index.tsx`, or remove the field kinds of a widget you
do not fetch;
[Field kinds](/documents/field-kinds#the-shipped-field-kinds) lists them.

</Step>
<Step>

### Render the document

`readDocument` checks the shape of what storage returns, and `createDocumentForm` turns the
document into a form component of your registry:

```tsx title="components/contact.tsx"
declare const stored: unknown
declare function send(answers: Record<string, unknown>): Promise<void>
// ---cut---
'use client'

import { readDocument } from '@formdef/document'
import { createDocumentForm } from '@formdef/document/react'

import { catalog } from '@/lib/formdef/field-kinds'

const ContactForm = createDocumentForm(readDocument(stored), catalog)

export const Contact = () => (
  <>
    <ContactForm id="contact" options={{ onSubmit: ({ value }) => send(value) }} />
    <button type="submit" form="contact">
      Send
    </button>
  </>
)
```

</Step>
</Steps>

- Each field renders with its field kind's widget, its `label`, its `description` as the
  widget's description, and whether it is required. Conditions, required fields and settings that follow an
  answer update as the answers change.
- The form starts with each field's empty value and validates with the document's
  [validator](/documents/validation-and-answers), so fields that do not show are not validated.
- A document with steps renders through the registered `structure.stepper`, such as the
  [stepper](/widgets/stepper) of the shadcn registry, which submits from the last step. A plain
  form has no button of its own: the `form` attribute points a button outside it at the form's
  `id`, as above.
- `createDocumentForm` throws when [`checkDocument`](/documents/builders#reading-and-checking)
  reports a problem with the document, and `readDocument` throws when the input is no form
  document, naming the path of the first problem.
- Create the form component once per document, not on every render: a component created anew
  remounts and loses what was entered. For a document that arrives as a prop, `useMemo` keyed by
  the document does that.
- The third argument takes the error texts as `messages` and `validation`, which works as the
  [`validation`](/guides/validation#when-the-schema-runs) of a config.
