---
title: Form documents
description: Describe a form as data, for form builders and forms stored in a database, and render it through your registry.
---

A typed config is how a form is written in code: the compiler checks every field against its
widget, and the form ships with the app. A **form document** is how a form is stored: JSON with a
format version that a builder writes and a database keeps, so the form changes without a deploy.
`@formdef/document` reads such a document, checks it, renders it through the widgets of your
registry and validates its answers, in the form and on a server.

| The form is | Write it as |
| --- | --- |
| written by a developer, as part of the app | a typed config |
| put together in a builder, or stored per customer in a database | a form document |

Nothing types a document's fields at compile time, so a document is checked when it is read. What
a field may be is decided in code, once: by the project's [field kinds](/documents/field-kinds).

## The shape

```json
{
  "format": 1,
  "items": [
    { "type": "field", "key": "f1", "kind": "text", "label": "Name", "required": true },
    {
      "type": "row",
      "items": [
        { "type": "field", "key": "f2", "kind": "email", "label": "Email" },
        { "type": "field", "key": "f3", "kind": "text", "label": "Phone" }
      ]
    },
    {
      "type": "section",
      "label": "Callback",
      "items": [
        { "type": "field", "key": "f4", "kind": "checkbox", "label": "Call me back" },
        {
          "type": "field",
          "key": "f5",
          "kind": "date",
          "label": "On",
          "description": "A weekday",
          "required": true,
          "visibleWhen": { "field": "f4", "op": "isTrue" }
        }
      ]
    }
  ]
}
```

- `format` is the version of the format the document was written with; `FORMAT_VERSION` is the
  one this release writes. A document of a newer format is refused when it is read.
- A document holds either `items`, a plain form, or `steps`, filled in one at a time. A step has a
  `key`, a `label`, an optional `description` under the label in the stepper, an optional
  `visibleWhen`, and its `items`.
- An item is a **field**, a **block** of content without an answer, a **row** of fields and blocks
  side by side, or a **section**: a `label` over its `items`, and an optional `description` under
  it. A section inside a section is a group that reads like one question, such as an address; a
  third level is not allowed. A row holds fields and blocks only.
- A block has a `key`, the `kind` of a registered [block kind](/documents/field-kinds#block-kinds),
  and optionally `settings` and `visibleWhen`. It gives no answer and is not validated; a condition
  cannot name it.
- A field has a `key`, the `kind` of a registered field kind and a `label`, and optionally a
  `description` between the label and the control, `required`, `visibleWhen`, `settings` and
  [`messages`](/documents/validation-and-answers#error-texts), its own error texts.
- **Keys** are generated by a builder and never shown. A field key is unique in the whole document,
  across steps too, and holds no dot or bracket, since it becomes a path in the form's values. The
  values of a document with steps are nested by step key, `{ s1: { f1: 'Ada' } }`; those of a
  plain form are flat.
- `required` is `true`, `false` (the default) or a condition. `visibleWhen` takes a condition on a
  step, section, row or field; without one, it always shows.
- `settings` holds the values of the field kind's [settings](/documents/field-kinds#settings), by
  name, such as the options of a choice or the unit of a number.

### Settings that follow an answer

A setting whose field kind marks it as `varies` may follow an answer. Its `cases` are checked in
order, and the value of the first whose condition holds applies; `otherwise` applies when none
does:

```json
{
  "type": "field",
  "key": "f7",
  "kind": "decimal",
  "label": "Living area",
  "settings": {
    "unit": {
      "cases": [{ "when": { "field": "f6", "op": "equals", "value": "o1" }, "value": "m²" }],
      "otherwise": "sq ft"
    }
  }
}
```

The field shows the unit that applies while the answers change; the validator and
[`describeAnswers`](/documents/validation-and-answers#describing-answers) use it too. A setting
whose field kind does not mark it takes a plain value.

### Texts that follow an answer

A text may follow an answer the same way, with `cases` and `otherwise`: the label and
description of a field, the description of a step or section, and the label and description of an
option. The labels of steps and sections stay fixed, since the stepper and the section show them
for the whole form.

```json
{
  "type": "field",
  "key": "f8",
  "kind": "number",
  "label": {
    "cases": [{ "when": { "field": "f6", "op": "equals", "value": "o1" }, "value": "Number of radiators" }],
    "otherwise": "Number of heating circuits"
  }
}
```

A condition of a text names a field that comes earlier, as every condition does. The case is
chosen first, then the language, then the placeholders.

### Placeholders

A text may name the answer of an earlier field as `{key}`, such as `"Thank you, {f1}."`. The
placeholder takes the answer as its value type writes it: text, a decimal or a date as entered, a
number, the label of the option chosen, the labels of several joined with commas. An answer that
is empty or does not show, and a boolean, give nothing. `{{` and `}}` write a brace.

Placeholders work in every text that may follow an answer, and in text settings. In a field's own
[error texts](/documents/validation-and-answers#error-texts) they name the issue's params and the
`label` instead. The labels of
steps and sections name no answers; `checkDocument` reports a placeholder there as `fixedText`, and
one on a field that does not exist or comes later as `unknownField` or `laterField`.

### Formatted descriptions

The descriptions of fields, options, sections and steps may carry limited formatting, written as
Markdown: `**bold**`, `*italics*`, links as `[text](https://…)` and paragraphs separated by a blank
line. A link opens only an `https:` or `mailto:` address, and a step's description shows its links
as text, since the stepper shows it inside a button. HTML stays text, and other Markdown, such as a
heading or a list, shows as its text. Labels stay plain.

### Languages

A document in several languages names them at the root, as language codes. Every text then takes
either a string, which holds for every language, such as a unit, or its translations:

```json
{
  "format": 1,
  "languages": ["de", "en"],
  "items": [
    {
      "type": "field",
      "key": "f1",
      "kind": "decimal",
      "label": { "de": "Wohnfläche", "en": "Living area" },
      "settings": { "unit": "m²" }
    }
  ]
}
```

- The texts are the labels and descriptions of steps, sections and fields, the labels and
  descriptions of options, and the values of a field kind's [text settings](/documents/field-kinds#settings),
  such as a placeholder.
- [`checkDocument`](/documents/builders#reading-and-checking) reports a translation that leaves out
  one of the languages, and one into a language the document does not name.
- `createDocumentForm`, `createValidator` and `describeAnswers` take a `language`. Without one, or
  with one the document does not name, the first language applies. A field kind's `props`
  receive its settings in that language, so no field kind deals with translations.

## Conditions

A condition compares one field, or combines conditions with `all` or `any`:

```json
{
  "any": [
    { "field": "f1", "op": "equals", "value": "o2" },
    { "field": "f4", "op": "atLeast", "value": 3 }
  ]
}
```

The field compared comes earlier in the document than the condition that names it. A field that
does not show counts as empty in the conditions after it, whatever value it still holds.

The operators belong to the value type of the field compared, and each says what it compares with,
as a setting: `op` is a name and `value` any JSON, and
[`checkDocument`](/documents/builders#reading-and-checking) checks both against the catalog. The
built-in value types have these:

| Value type | Operators | `value` |
| --- | --- | --- |
| `text` | `isFilled`, `isEmpty` | none |
| `choice` | `equals`, `notEquals` | an option's value |
| | `in`, `notIn` | a list of option values |
| | `isFilled`, `isEmpty` | none |
| `choices` | `includes`, `excludes` | an option's value |
| | `isFilled`, `isEmpty` | none |
| `boolean` | `isTrue`, `isFalse`, `isFilled`, `isEmpty` | none |
| `number`, `decimal` | `equals`, `notEquals`, `lessThan`, `atMost`, `greaterThan`, `atLeast` | a number |
| | `isFilled`, `isEmpty` | none |
| `date` | `equals`, `before`, `onOrBefore`, `after`, `onOrAfter` | a date as an ISO string, such as `2026-05-01` |
| | `isFilled`, `isEmpty` | none |
| a [value type of your own](/documents/field-kinds#value-types) | its own operators, `isFilled`, `isEmpty` | what each operator compares with |

- An empty field equals nothing and comes in no order, so of the comparisons only `notEquals`,
  `notIn` and `excludes` hold for it.
- A boolean counts as filled only when it is true: `isFalse` holds for a checkbox left unticked.
- A decimal is compared as a number, and a date with a time by its day.

A builder offers only the operators of the field's value type and renders the input for `value`
from the operator's setting; `checkDocument` reports an operator the value type does not have and
a `value` that does not fit, is missing, or is given to an operator that compares with nothing.

## A first form

<Steps>
<Step>

### Install the package

```npm
npm install @formdef/document @formdef/core @tanstack/react-form
```

</Step>
<Step>

### Fetch the field kinds

After the [setup](/installation#the-widgets-for-shadcn), fetch the field kinds of the shadcn
registry:

```npm
npx shadcn@latest add @formdef/field-kinds
```

It writes `lib/formdef/field-kinds.ts`, which exports them as a `catalog`. Its field kinds name the
widgets `text`, `textarea`, `number`, `checkbox`, `radio`, `select`, `checkboxes` and `date`.
Register each under that name in `lib/formdef/index.tsx`, or remove the field kinds of a widget you
do not fetch;
[Field kinds](/documents/field-kinds#the-shipped-field-kinds) lists them.

</Step>
<Step>

### Render the document

`readDocument` checks the shape of what storage returns, and `createDocumentForm` turns the
document into a form component of your registry:

```tsx title="components/contact.tsx"
declare const stored: unknown
declare function send(answers: Record<string, unknown>): Promise<void>
// ---cut---
'use client'

import { readDocument } from '@formdef/document'
import { createDocumentForm } from '@formdef/document/react'

import { catalog } from '@/lib/formdef/field-kinds'

const ContactForm = createDocumentForm(readDocument(stored), catalog)

export const Contact = () => (
  <>
    <ContactForm id="contact" options={{ onSubmit: ({ value }) => send(value) }} />
    <button type="submit" form="contact">
      Send
    </button>
  </>
)
```

</Step>
</Steps>

- Each field renders with its field kind's widget, its `label`, its `description` as the
  widget's description, and whether it is required. Conditions, required fields and settings that follow an
  answer update as the answers change.
- The form starts with each field's empty value and validates with the document's
  [validator](/documents/validation-and-answers), so fields that do not show are not validated.
- A document with steps renders through the registered `structure.stepper`, such as the
  [stepper](/widgets/stepper) of the shadcn registry, which submits from the last step. A plain
  form has no button of its own: the `form` attribute points a button outside it at the form's
  `id`, as above.
- `createDocumentForm` throws when [`checkDocument`](/documents/builders#reading-and-checking)
  reports a problem with the document, and `readDocument` throws when the input is no form
  document, naming the path of the first problem.
- Create the form component once per document, not on every render: a component created anew
  remounts and loses what was entered. For a document that arrives as a prop, `useMemo` keyed by
  the document does that.
- The third argument takes the error texts as `messages` and `validation`, which works as the
  [`validation`](/guides/validation#when-the-schema-runs) of a config.
